    Revolushower — Mapa de ativações do Master¶

    Atualizado em 2026-09-07.

    Este documento separa a origem de uma solicitação, a validação de segurança, o acionamento físico e a confirmação do resultado. “Ativação” significa uma solicitação que pode levar a bomba a ser ligada; não significa que qualquer canal tenha autorização para comandar o GPIO diretamente.

    Regra central¶

    Todas as origens devem convergir para o Command Gateway e, depois, para o Safety/Action Kernel. Somente o kernel pode controlar a bomba e o aquecedor. O Master é a autoridade final: backend, aplicativo, Alexa, painel e scheduler apenas solicitam.

    flowchart LR
    B[Botão local] --> G[Command Gateway]
    F[Sensor de fluxo] --> G
    R[Rádio local / Node] --> G
    M[App mobile] --> API[Backend/API]
    P[Painel administrativo] --> API
    A[Alexa futura] --> API
    S[Scheduler futuro] --> API
    API --> T[MQTT/HTTPS autenticado]
    T --> G
    G --> V[Validação local do Master]
    V --> K[Safety/Action Kernel]
    K --> GPIO[Relé da bomba / relé do aquecedor]
    K --> E[Estado, resultado e eventos]
    E --> T
    E --> API
    API --> M
    API --> P
    API --> A

    Origens de ativação¶

    Origem Quem inicia Situação atual Transporte Evento/origem esperado
    LOCAL_BUTTON botão físico do Master implementado GPIO local local
    FLOW_SENSOR sensor binário de fluxo implementado GPIO local sensor_fluxo_agua
    RADIO_LOCAL Node pareado legado preservado ESP-NOW remoto
    LEGACY_WEB painel/backend antigo implementado, somente referência polling HTTP web
    MOBILE aplicativo Revolushower futuro API → MQTT/contrato novo MOBILE
    ADMIN painel interno futuro API → MQTT/contrato novo ADMIN ou origem auditada
    SCHEDULE scheduler do backend futuro API/worker → MQTT SCHEDULE
    ALEXA Alexa, se aprovada hipótese futura adaptador → API → MQTT ALEXA

    O backend novo deve preservar a origem original e a identidade do ator. MOBILE, ADMIN, SCHEDULE e ALEXA não devem ser reduzidos a um genérico web.

    O que acontece em cada origem¶

    Botão local¶

    O usuário pressiona o botão de ação do Master. O firmware solicita um ciclo com o delay e a duração persistidos localmente. O kernel verifica bomba ocupada, cooldown, bloqueio do aquecedor e demais regras. Se aceito, aciona a bomba após o delay.

    Sensor de fluxo¶

    O sensor indica fluxo (LOW no hardware atual). O Master solicita a bomba. Se o fluxo desaparecer durante o delay, o pedido pode ser cancelado. Com fluxo ativo, a bomba pode passar ao controle do sensor; quando o fluxo cessa, o Master encerra o ciclo e registra a duração.

    O sensor não é um comando de usuário nem uma confirmação de que uma solicitação remota foi executada. É uma origem física independente.

    Rádio local / Node¶

    O Master recebe ACIONAR de um Node pareado, valida o pareamento e agenda o ciclo. A origem atual é registrada como remoto. Este caminho é legado da Fase 1 e permanece preservado, embora sua segurança ESP-NOW ainda tenha riscos documentados.

    Backend legado¶

    O painel antigo cria uma pending request. O Master consulta a cada 10 segundos:

    GET /pending-requests/current/{deviceId}

    Se encontra um id novo, usa os tempos locais, agenda o acionamento e envia done antes do fim real do ciclo. Esse fluxo foi validado em 2026-09-07, mas não será usado no novo produto.

    App mobile, painel, scheduler e Alexa¶

    Esses canais não devem acionar GPIOs nem falar diretamente com o broker. Eles criam comandos autenticados no backend. O backend autoriza, registra, ordena e publica a solicitação para o Master. O resultado só é apresentado como sucesso depois da confirmação do Master.

    Um comando futuro terá, no mínimo:

    {
  "requestId": "globalmente-unico",
  "installationId": "...",
  "deviceId": "...",
  "command": "START_PREHEAT",
  "origin": "MOBILE",
  "actorId": "...",
  "issuedAt": "...",
  "expiresAt": "...",
  "expectedStateVersion": 12
}

    Estados do ciclo¶

    stateDiagram-v2
    [*] --> READY
    READY --> PUMP_DELAY: solicitação aceita + delay
    READY --> PUMP_ACTIVE: solicitação aceita sem delay
    READY --> PUMP_DELAY: fluxo detectado
    PUMP_DELAY --> READY: fluxo cessa / cancelamento válido
    PUMP_DELAY --> PUMP_ACTIVE: delay termina
    PUMP_ACTIVE --> FLOW_ACTIVE: duração eletrônica termina + fluxo presente
    PUMP_ACTIVE --> READY: duração termina sem fluxo
    FLOW_ACTIVE --> READY: fluxo cessa
    PUMP_ACTIVE --> COOLDOWN: watchdog/limite
    FLOW_ACTIVE --> COOLDOWN: watchdog/limite
    FLOW_ACTIVE --> HEATER_BLOCKED: fluxo contínuo excede limite
    HEATER_BLOCKED --> READY: bloqueio termina
    COOLDOWN --> READY: cooldown termina

    AP_MODE, PAIRING_MODE e OFFLINE são condições de conectividade/configuração e não substituem os estados físicos do ciclo.

    Monitoramento correto¶

    O novo sistema deve observar quatro coisas separadamente:

    Camada Pergunta Evidência
    Intenção alguém solicitou? comando com requestId, origem e ator
    Transporte o Master recebeu? RECEIVED/ack autenticado
    Segurança o Master aceitou? ACCEPTED ou rejeição com motivo
    Física o ciclo ocorreu? transições e estado confirmado do Master

    Um registro done do backend não pode substituir essas quatro evidências.

    Distinção entre histórico e confirmação¶

    Eventos como local, web e sensor_fluxo_agua descrevem a origem observada, mas sozinhos não provam toda a execução. O novo contrato deverá relacionar cada evento a:

    • requestId, quando houver solicitação;
    • origin e actorId;
    • estado anterior e novo estado;
    • instante de aceitação, início e fim;
    • motivo de rejeição ou falha;
    • versão do estado do Master.

    Leituras manuais do painel legado são registros administrativos, não eventos confirmados pelo equipamento.

    Situação atual versus desenho novo¶

    flowchart TB
    subgraph Atual[Implementado / legado]
      L1[Botão] --> AK1[ActionManager]
      L2[Fluxo] --> AK1
      L3[ESP-NOW] --> AK1
      L4[HTTP polling] --> AK1
      AK1 --> GPIO1[GPIOs]
      AK1 --> H1[POST /reads]
    end
    subgraph Novo[Alvo da Fase 1]
      N1[Botão / fluxo / rádio] --> GW[Command Gateway]
      N2[Mobile / painel / scheduler / Alexa] --> API2[API + autorização]
      API2 --> MQTT[MQTT seguro]
      MQTT --> GW
      GW --> SK[Safety/Action Kernel]
      SK --> GPIO2[GPIOs]
      SK --> ST[Snapshot + resultado confirmado]
      ST --> MQTT
      MQTT --> API2
    end

    O desenho novo não transforma o backend em autoridade física. Ele organiza as solicitações e a auditoria; a decisão final continua no Master.

    Lacunas que ainda precisam de bancada ou decisão¶

    • cancelamento durante delay e durante bomba ativa;
    • prioridade entre fluxo, botão, rádio e comando remoto concorrentes;
    • semântica exata de maxOnSensorMs para cada origem;
    • estados elétricos no boot, reset, brownout e perda de Wi-Fi;
    • confirmação de fluxo quantitativo: o sensor atual é apenas binário;
    • política offline para comandos agendados;
    • limites configuráveis remotamente e seus papéis autorizados.
