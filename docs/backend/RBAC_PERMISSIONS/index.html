    Revolushower — Catálogo de permissões e administração de perfis¶

    Atualizado em: 2026-09-22 Tipo: fonte atual e normativo. A seção 1 e a 2 descrevem o RBAC anterior a esta entrega e ficam como registro do ponto de partida; da seção 4 em diante está o catálogo e a tela já implementados (ver §9). Escopo: backend backend/src/rbac.js + backend/src/server.js e painel administrativo frontend/src/. O canal mobile/cliente é mapeado para completude, mas não é editável na tela proposta. Fonte de verdade: o código. Toda linha citada foi conferida no checkout em 2026-09-22.

    1. Estado atual do RBAC¶

    1.1 Papéis existentes¶

    Papel Origem Onde é criado Editável na tela proposta

    ADMIN enum user_role (001_initial.sql:5) convite (/api/users/invitations) Sim
    INSTALLER enum user_role (001_initial.sql:5) convite (/api/users/invitations) Sim

    1.2 Permissões codificadas hoje¶

    READ_DEVICE ✓ ✓ ✓ ✓ ✓ ✓
    OPERATE_DEVICE ✓ ✓ ✓ ✓ ✓ ✓
    CONFIGURE_DEVICE ✓ ✓ ✓ — — ✓

    ACTIVATE_DEVICE ✓ ✓ — — — ✓

    A verificação é rbac.can(principal, chave) — comparação direta de principal.role contra a lista. Não há persistência: a matriz é literal congelado (Object.freeze) no código.

    1.3 Camadas de autorização que existem além do RBAC¶

    O RBAC é só uma das quatro camadas. Elas precisam ser mantidas separadas — a tela de permissões só governa a camada 2.

    1. Autenticação/sessão — auth.js, resolução de principal em database.js; sessões permanentes até logout/revogação.
    2. RBAC por papel — rbac.can(). É o que esta funcionalidade passa a administrar.
    3. Escopo por linha — database.js:544-556 (scopeClause): INSTALLER só vê instalações atribuídas, CLIENT só as de client_installation_access, MOBILE_* só as de mobile_installation_members. Isso não é permissão e não deve ser editável — é isolamento de dados.
    4. Regras de negócio adicionais — ex.: database.js:529-533 impede revogar MASTER_ADMIN, exige MASTER_ADMIN/TEST_ADMIN para revogar ADMIN e impede revogar o último admin ativo. Continuam valendo mesmo que a permissão seja concedida.

    3. Divergências e achados (o que "despadronizado" significa concretamente)¶

    3.1 Segurança — exigem decisão antes da implementação¶

    • TEST_ADMIN era um Master Admin sombra, e a origem dele é um Bearer estático. Aparecia nas 9 permissões, inclusive MANAGE_ADMINS, e em database.js:530 podia revogar ADMIN. Nenhum fluxo do produto cria usuário com esse papel: o único emissor é server.js, em authenticateRequest() — quando o Authorization bate com a variável API_AUTH_TOKEN, a requisição recebia o principal { role: 'TEST_ADMIN', userId: null }. Ou seja, API_AUTH_TOKEN é uma credencial permanente de privilégio total, sem usuário atribuído, e backend/README.md já registrava que o APK de teste não precisa mais dela. Achado correlato em docs/audits/DOC_CODE_AUDIT_2026-09-22.md. Resolvido nesta entrega: o papel foi removido de rbac.js, database.js e do frontend. O token estático continua funcionando com o mesmo alcance efetivo de antes, agora declarado pelo que sempre foi (role: 'MASTER_ADMIN'), para não quebrar automação existente. O valor TEST_ADMIN permanece no enum user_role do Postgres porque o PostgreSQL não remove valor de enum sem recriar o tipo — nenhum código o concede mais. Desativar ou rotacionar o API_AUTH_TOKEN é decisão separada, registrada em SEC-004.
    • GET /metrics é público. Expõe uptime, estado MQTT, prontidão do banco e tamanho dos caches sem autenticação, antes do gate de sessão.
    • PATCH /api/installations/:id exige apenas READ_DEVICE. Como READ_DEVICE inclui CLIENT, MOBILE_OWNER e MOBILE_MEMBER, uma conta de app com acesso a uma instalação pode alterar o endereço cadastral dela. É escrita administrativa atrás de permissão de leitura.
    • POST /api/installations/:id/photos exige apenas READ_DEVICE. Qualquer conta com acesso à instalação pode gravar evidência de instalação — que é insumo do checklist de ativação.
    • GET /api/dashboard, GET /api/installations e GET /api/installations/:id não têm verificação de permissão. Hoje isso é contido pelo escopo por linha, mas significa que não existe permissão a conceder ou retirar — a tela precisa de uma chave real para governar.

    3.2 Padronização — nomes que não descrevem o que guardam¶

    • MANAGE_INSTALLERS guarda listar usuários, status do e-mail do sistema e revogar usuário — três coisas que não são "gerenciar instaladores".
    • MANAGE_INSTALLATIONS guarda a auditoria global, enquanto a auditoria de uma instalação usa READ_DEVICE. Mesma natureza de dado, permissões diferentes.
    • READ_DEVICE virou permissão-coringa: guarda leitura de dispositivo, leitura de evidência, upload de evidência, edição de instalação e execução de diagnóstico.
    • Granularidade por comando MQTT vive inline no handler (server.js:645-646), não no catálogo.
    • O canal mobile ignora o RBAC e usa listas literais em 8 rotas.

    3.3 Frontend — menu não reflete permissão¶

    frontend/src/auth.tsx:11 define isAdmin() com a lista literal ['MASTER_ADMIN','ADMIN','TEST_ADMIN'], e layout.tsx usa esse único booleano para mostrar/esconder Clientes, Usuários, Auditoria e OTA. Se o Master Admin retirar MANAGE_OTA do perfil ADMIN, o backend passa a negar mas o menu continua exibindo OTA. Sem permissões efetivas vindas do servidor, a tela de administração não tem efeito visível.

    3.4 Coerência de produto — a confirmar com o owner¶

    INSTALLER hoje tem CONFIGURE_DEVICE e OPERATE_DEVICE, mas não tem ACTIVATE_DEVICE nem MANAGE_INSTALLATIONS — ou seja, configura e calibra, mas não conclui o checklist nem ativa o equipamento que instalou. Pode ser intencional (ativação é aprovação administrativa) ou lacuna. A tela proposta permite corrigir sem deploy, mas o padrão de fábrica precisa ser decidido.

    4. Catálogo padronizado proposto (arquitetura-alvo)¶

    4.1 Convenção de nomes¶

    contexto.recurso.acao, minúsculo, pontos como separador. O prefixo é o contexto/tela, o sufixo é a ação (view, list, create, update, delete, ou verbo específico como activate, publish, unlock).

    Vantagem sobre as 9 chaves atuais: o nome diz a qual tela pertence, permite agrupar a UI automaticamente por prefixo e separa leitura de escrita sem inventar sinônimos.

    4.2 Compatibilidade com as 9 chaves legadas¶

    As chaves atuais não são removidas de imediato. rbac.can() passa a aceitar tanto a chave nova quanto a legada, resolvendo a legada para o conjunto de chaves novas que a substituem:

    Legada Equivale a
    READ_DEVICE device.view, device.state.view, device.events.view, device.firmware.view, device.commands.list, device.command.result.view, device.diagnostic.run, configuration.view, configuration.request.view, evidence.list, evidence.download, activation.checks.view, installations.audit.view, dashboard.view, installations.list, installations.view
    OPERATE_DEVICE device.preheat.start, device.command.send
    CONFIGURE_DEVICE configuration.update
    MANAGE_OTA ota.*
    MANAGE_ADMINS users.invite.admin
    MANAGE_INSTALLERS users.list, users.invite.installer, users.revoke, installations.installers.assign, installations.installers.revoke, system.email.view
    MANAGE_INSTALLATIONS installations.create, installations.update, activation.checks.update, configuration.calibration.unlock, audit.view
    MANAGE_CUSTOMERS customers.*, installations.customers.*
    ACTIVATE_DEVICE activation.activate, activation.deactivate

    A migração dos pontos de chamada é feita rota a rota, com teste, sem alterar o resultado prático das guardas existentes — exceto nos pontos marcados como correção em §3.1, que são mudanças deliberadas de comportamento e precisam de aprovação.

    5. Desenho da funcionalidade¶

    5.1 Modelo de dados¶

    Uma tabela nova, sem alterar nenhuma existente:

    role_permissions (
  role       user_role   NOT NULL,
  permission text        NOT NULL,
  allowed    boolean     NOT NULL,
  updated_at timestamptz NOT NULL DEFAULT now(),
  updated_by uuid REFERENCES users(id),
  PRIMARY KEY (role, permission)
)

    Regras de resolução, nesta ordem:

    1. MASTER_ADMIN → sempre permitido; a tabela não é consultada.
    2. Existe linha (role, permission) → vale allowed.
    3. Não existe linha → vale o padrão de fábrica do código (§4.4).

    Consequência desejada: o catálogo continua sendo definido em código (não há como um DELETE no banco criar uma permissão fantasma nem apagar uma existente), e o banco guarda apenas as exceções ao padrão. Um banco vazio se comporta exatamente como o sistema de hoje.

    5.2 Backend¶

    • backend/src/permissions.js (novo) — catálogo (chave, rótulo, contexto, sensível), padrão de fábrica e mapa de compatibilidade legado→novo. Módulo puro, sem I/O, testável isoladamente.
    • backend/src/rbac.js — passa a consultar um override em memória carregado do banco; can() aceita chave nova ou legada. Mantém a assinatura can(principal, key) para não tocar nos ~50 pontos de chamada de uma vez.
    • Cache — a matriz efetiva fica em memória e é recarregada na inicialização, a cada gravação, e por TTL curto (60 s) para cobrir o cenário de mais de uma instância do backend. Sem cache, cada rota faria uma consulta extra ao banco.
    • Rotas novas
    • GET /api/permissions → { catalog: [...], roles: ['ADMIN','INSTALLER'], matrix: { ADMIN: {...}, INSTALLER: {...} }, defaults: {...} } — guarda system.permissions.view.
    • PUT /api/permissions → corpo { role, changes: { chave: boolean } }; guarda system.permissions.update; valida que role ∈ {ADMIN, INSTALLER} e que toda chave existe no catálogo; recusa system.permissions.*; grava em transação e registra em audit_events (uma entrada por alteração, com before_data/after_data).
    • GET /api/auth/me → passa a devolver também permissions: [...] (as permissões efetivas do principal), para o frontend montar o menu sem adivinhar.
    • Auditoria — ação ROLE_PERMISSION_CHANGED, entidade role_permission. Alteração de permissão é evento de segurança e precisa de rastro individual.

    5.3 Trava anti-bloqueio¶

    Três regras que o backend recusa mesmo para o MASTER_ADMIN:

    1. MASTER_ADMIN não é editável — não aparece como coluna.
    2. system.permissions.view e system.permissions.update não são concedíveis a nenhum perfil pela tela. Não há caminho em que o Master Admin delegue a administração de permissões e depois não consiga revertê-la.
    3. users.invite.admin e users.revoke permanecem sujeitas às regras de database.js:527-536 (não revogar MASTER_ADMIN, não revogar o último admin ativo) — conceder a permissão não desliga a regra de negócio.

    5.4 Frontend — tela /permissoes¶

    Entrada no menu lateral, visível apenas com system.permissions.view.

    • Layout: matriz. Linhas agrupadas por contexto (accordion, contexto expansível), colunas Administrador e Instalador, célula = checkbox. Cabeçalho fixo ao rolar.
    • Por contexto: checkbox tri-estado no cabeçalho do grupo para marcar/desmarcar o contexto inteiro.
    • Célula: mostra o valor efetivo; quando difere do padrão de fábrica, recebe marca visual "alterado" e o padrão aparece no tooltip.
    • Gravação explícita: as alterações ficam pendentes até Salvar; o botão mostra a contagem de mudanças e abre um resumo antes de confirmar. Permissões sensíveis (§4.3) aparecem destacadas nesse resumo. Há Descartar e Restaurar padrão de fábrica (por contexto e global).
    • Reflexo imediato: após salvar, GET /api/auth/me é reconsultado e o menu do usuário corrente é remontado.
    • isAdmin() é substituído por can(user, 'chave') derivado de user.permissions. layout.tsx passa a decidir cada item de menu pela permissão correspondente (customers.list, users.list, audit.view, ota.jobs.list, system.permissions.view) em vez do booleano único. Sem isso a tela não produz efeito visível (§3.3).
    • Sessões já abertas: a mudança vale no backend imediatamente; o menu de um usuário já logado só se ajusta no próximo GET /api/auth/me (troca de rota ou refetch por foco de janela, já configurado em App.tsx). Isso é aceitável porque a negação real é sempre do servidor — mas precisa constar na tela, para o Master Admin não achar que a mudança não pegou.

    Riscos principais

    1. Regressão silenciosa de autorização ao migrar ~50 pontos de chamada. Mitigação: o padrão de fábrica é derivado mecanicamente da matriz atual, e o teste cobre a equivalência legado × novo permissão a permissão antes de qualquer troca de comportamento.
    2. Auto-bloqueio do Master Admin. Mitigado por §5.3.
    3. Múltiplas instâncias do backend com cache divergente por até 60 s. Aceitável para uma decisão administrativa; documentado na tela.
    4. Mudança deliberada de comportamento em installations.update e evidence.upload (§3.1): contas de app que hoje conseguem essas ações deixarão de conseguir. É correção de segurança, mas é mudança de contrato e precisa de aprovação do owner antes de implementar.
