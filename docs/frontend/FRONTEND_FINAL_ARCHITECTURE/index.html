    Arquitetura do Frontend Final Revolushower¶

    Status: decisão arquitetural aprovada para a próxima implementação Data: 2026-09-12

    1. Contexto¶

    O frontend atual foi construído como protótipo incremental em HTML e JavaScript. Ele não deve ser evoluído como base de produção, pois múltiplos blocos sobrescritos de código causam regressões, inconsistência de estado, handlers duplicados e dificuldade de teste.

    A próxima versão será um sistema final, usado por administradores em desktop e por instaladores em navegador móvel.

    2. Decisão¶

    Adotar uma aplicação React com TypeScript, roteamento explícito e arquitetura de componentes. A aplicação será responsiva e distribuída como PWA, mantendo a possibilidade de empacotamento futuro para Android/iOS.

    O backend Node.js, PostgreSQL, contratos MQTT e firmware Master permanecem como camadas separadas e não serão substituídos por lógica no frontend.

    3. Stack recomendada¶

    • React + TypeScript;
    • Vite para build e desenvolvimento;
    • React Router para URLs reais e recuperação por F5;
    • TanStack Query para requisições, invalidação e sincronização controlada;
    • React Hook Form + Zod para formulários e validação;
    • biblioteca de componentes responsivos e acessíveis;
    • Vitest para testes unitários;
    • Playwright para testes reais de navegador desktop e mobile;
    • PWA somente para instalação, câmera e conveniência, sem cache de dados operacionais.

    4. Regras de segurança¶

    • Todo acesso passa pela API HTTPS.
    • O frontend nunca acessa MQTT, banco ou credenciais de infraestrutura.
    • Tokens não devem ser gravados em localStorage; usar cookie seguro HttpOnly/SameSite quando o backend estiver preparado para isso.
    • CORS deve permitir somente origens aprovadas.
    • Permissões devem ser verificadas no backend; o frontend apenas oculta ações não autorizadas.
    • Toda ação crítica exige resposta confirmada do backend/Master.
    • Não exibir stack trace, SQL, códigos internos ou credenciais ao usuário.
    • Upload deve validar tipo, tamanho, conteúdo e autorização no servidor.
    • Logs do navegador não podem conter tokens, senhas ou dados pessoais desnecessários.
    • CSP, HSTS, TLS moderno, proteção contra XSS e headers de segurança são obrigatórios.

    5. Navegação¶

    Rotas:

    • /login;
    • /dashboard;
    • /clientes e /clientes/:id;
    • /instalacoes;
    • /instalacoes/nova;
    • /instalacoes/:id;
    • /usuarios;
    • /auditoria;
    • /ota.

    Cada rota deve ser acessível diretamente e funcionar após F5. O servidor deve entregar o shell da aplicação para rotas válidas e uma página controlada para rotas inválidas.

    6. Modelo de estado¶

    Não usar estado duplicado por componente para dados operacionais. A fonte de verdade será:

    • servidor/API para cadastros e estados persistidos;
    • TanStack Query para leitura, sincronização e invalidação;
    • estado local somente para formulário, modal e interação transitória;
    • máquina de estados para comandos assíncronos.

    Um comando deve possuir os estados idle, sending, published, waiting, completed, rejected, failed, expired ou invalid. A interface deve mapear cada estado para uma mensagem humana.

    7. Tela de detalhe da instalação¶

    A tela será composta por componentes estáveis:

    • InstallationHeader;
    • DeviceDetailsCard;
    • ConfigurationCard;
    • DeviceOperationsCard;
    • CustomerLinksCard;
    • EvidenceCard;
    • ActivationChecklistCard;
    • ActionLogCard.

    Os blocos superiores “Detalhes” e “Configuração” mantêm posição fixa.

    O bloco de configuração exibirá somente valores confirmados pelo Master. A edição será individual por tempo, com confirmação, invalidação da consulta e atualização do log.

    Nenhuma operação deve simplesmente desabilitar o botão sem apresentar progresso e resultado.

    8. Experiência móvel do instalador¶

    • layout mobile-first;
    • alvos de toque de no mínimo 44px;
    • formulários em uma coluna;
    • botões críticos destacados e separados;
    • câmera do celular para evidências;
    • preview antes do envio;
    • compressão controlada sem destruir legibilidade;
    • upload retomável ou mensagem clara de falha;
    • suporte a conexão instável;
    • estados offline e online explícitos;
    • não armazenar comandos para execução posterior sem política aprovada;
    • confirmação visual após cada ação do Master.

    9. Evidências¶

    O componente deve carregar imagens pela API autenticada, nunca por URL pública sem proteção. Deve apresentar upload, progresso, erro, sucesso, miniaturas em duas colunas no celular e abertura da imagem original.

    O checklist deve refletir a existência da evidência e informar o que ainda falta para ativação.

    10. Comandos remotos¶

    Criar um único CommandService no frontend. Ele será responsável por:

    1. chamar a API;
    2. guardar requestId;
    3. acompanhar o resultado;
    4. mapear códigos técnicos para mensagens;
    5. invalidar consultas de instalação, configuração e log;
    6. restaurar o controle da interface;
    7. impedir comandos duplicados acidentais.

    Nenhum componente poderá implementar seu próprio polling ou interpretação de resultado.

    11. Cache e atualização¶

    O PWA pode armazenar somente shell, ícones e recursos estáticos. Dados de instalação, configuração, estado, log, clientes e OTA devem sempre ser lidos da API conforme política explícita.

    Após qualquer mutação, invalidar as queries relacionadas e buscar o estado confirmado. Não usar atualização otimista para ativação, tempos, estado físico ou resultado de comando.

    12. Testes obrigatórios¶

    • unitários de validação, permissões e mapeamento de mensagens;
    • componentes com loading, vazio, sucesso, erro e timeout;
    • Playwright desktop;
    • Playwright mobile com viewport e câmera simulada;
    • login e sessão expirada;
    • F5 em todas as rotas;
    • CRUD de clientes;
    • criação e detalhe de instalação;
    • edição de cada tempo;
    • leitura de firmware e configuração;
    • cancelamento com e sem ciclo ativo;
    • upload e abertura de evidências;
    • checklist e ativação;
    • OTA;
    • usuário administrador e instalador;
    • dispositivo offline, MQTT indisponível, resposta atrasada e duplicidade;
    • regressão antes de cada publicação.

    13. Critério de produção¶

    O frontend só será considerado pronto quando não houver código duplicado de tela, todos os comandos usarem o mesmo serviço, todas as rotas funcionarem por URL direta, todos os erros forem tratados e a bateria de testes de navegador passar em desktop e mobile.

    O protótipo atual deve permanecer disponível apenas como referência temporária, não como fonte de produção.
